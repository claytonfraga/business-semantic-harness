# Regras de execução do BSH

- Use `/usr/bin/rtk` em comandos de terminal.
- Em testes funcionais E2E do BSH, abra `bsh codex` a partir da pasta do piloto em uma sessão persistente `tmux` ou `herdr`. O processo do agente deve receber solicitações reais e tentar modificar uma cópia limpa do piloto; chamadas HTTP diretas ao servidor não substituem esse teste.
- Execute pelo menos dois casos especificados antes do teste: uma mudança de código aderente à ontologia/SHACL e uma mudança que contrarie uma regra. Compare o estado inicial, as ações propostas, perguntas ao usuário, decisões, arquivos finais e auditoria.
- Valide a ontologia antes da sessão. Se `bsh codex` recusar iniciar, registre o diagnóstico e marque ambos os casos como **bloqueados antes do primeiro turno**; não chame isso de teste funcional aprovado e não use Codex direto como substituto.
- Guarde um relatório datado em `pilot/asset-management/evaluation/` com os prompts, procedimento, evidências, resultados esperados/observados, limitações e correções propostas. Encerre a sessão persistente após coletar as evidências.
- Derive qualquer teste automatizado novo apenas do OpenSpec, depois da implementação, com nomes no formato Given/When/Then. Não use TDD.
- Antes de qualquer push (e portanto antes de acionar o CI/CD no GitHub Actions), execute localmente `npm run quality`, `npm test` e `npm run test:e2e`; prossiga apenas se todos passarem. O CI/CD no GitHub só é acionado depois da validação local.
- Nomeie os testes por agente: prefixe com `agy:` os testes do adaptador Agy e `codex:` os do adaptador Codex; quando houver E2E por agente, use o prefixo correspondente no nome do arquivo (`agy-*` / `codex-*`). Todo teste de fumaça SHALL incluir `smoke` como parte do prefixo (por exemplo `agy-smoke-*`/`codex-smoke-*` em arquivos ou `agy: smoke ...` no nome do teste).
- Toda ontologia de domínio pertence ao projeto a que se refere e vive em `<projeto>/.bsh/domains/<dominio>/` (`ontology.jsonld` e `shapes.ttl`). Nunca mova nem copie a ontologia de um projeto para o pacote BSH, para outro projeto ou para um diretório global. As fixtures em `test/fixtures/` são ontologias sintéticas do próprio BSH para testes unitários, não ontologias de projeto. Ao abrir uma sessão (mesmo em cópia limpa), o projeto selecionado precisa conter sua própria ontologia validada.
- Todo teste E2E e de fumaça registra captura de tela do tmux em `screenshots/` com nome descritivo, e apresenta ao final os tokens gastos a mais pelo harness BSH (verificação ontológica) e a economia em relação ao Codex direto, em valores absolutos e percentuais.
